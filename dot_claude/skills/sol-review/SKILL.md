今回の変更を、t3-code の `delegate_task` で別プロバイダーの Sol に**独立・敵対的**にレビューさせる。

- **独立**: Sol は実装者（あなた）の説明や自己評価を受け取らず、要求と差分だけから自力で正否を判断する。
- **敵対的**: Sol は変更を壊しにいく攻撃者として振る舞い、変更が誤っている証拠を探す。

## 1. レビュー範囲を確定する

`git status` と `git diff`（必要ならベースブランチとの差分）で、レビュー対象の変更ファイルを把握する。引数があればそれをレビュー範囲・重点観点として優先する。差分がなければ、その旨を伝えて終了する。

**要求**を集める。独立とは実装者の解釈から独立することで、要件からではない。要件は一次資料のまま渡す:

- チケット（Linear / GitHub Issue など）があれば、タイトル・本文・受け入れ条件・関連コメントを**原文のまま**転記し、URL を添える。Sol 側から参照できるとは限らないため、リンクだけで済ませず本文を貼る。
- チケット外でユーザーが追加・変更した要求は、ユーザーの発言を原文に近い形で併記する。
- 要約・言い換えで原文を置き換えない（実装者の解釈が混ざる）。

## 2. 依頼する

`delegate_task` を次の設定で呼ぶ。

- target: providerInstanceId=`codex`, model=`gpt-6.1-sol`, options: reasoningEffort=`high`
- role=`review`, mode=`async`, title=`Sol レビュー: <変更の要約>`
- clientRequestId: ラウンドごとに新しい値（同じラウンドのリトライでは同じ値）

task プロンプトは Sol が単独で読んで動ける自己完結の内容にする（親の会話は引き継がれない）。渡すのは**事実だけ**:

- 作業ディレクトリの絶対パスと、差分の確認コマンド
- 手順 1 の要求
- 引数で指定された重点観点（あれば）

実装の方針説明、設計判断の理由、「テスト済み」「問題ないはず」といった自己評価は**入れない**。Sol の判断を実装者の見方に寄せないためである。

続けて、次の指示をそのまま含める。

> あなたは敵対的レビュアーです。この変更にはバグがあると仮定し、それを見つけて実証することが仕事です。
> - 差分だけでなく、呼び出し元・呼び出し先・関連テストまで読み、変更が要求を本当に満たすか自力で判断する。
> - 要件の各項目・受け入れ条件について、満たしている / いないを根拠付きで判定する。
> - 攻撃の観点: 要求の取りこぼし、境界値と異常入力、エラー経路、並行性・状態、既存の公開 API と呼び出し元の破壊、セキュリティ、テストが本当に挙動を検証しているか。
> - 主張は反証可能な形で: 各指摘に、具体的な入力・状態 → 誤った結果、という失敗シナリオを付ける。可能ならテストや型チェックを実行して実証する。
> - あなたは読み取り専用です。ファイル編集・コミット・依存の追加は行わない（テスト実行で生成される一時ファイルは可）。
> - 出力（日本語）: 指摘ごとに「重大度（Critical/High/Medium/Low） / ファイル:行 / 問題 / 失敗シナリオ / 実証方法と結果 / 修正案」。確信度が低いものも「要確認」として出す。最後に、攻撃したが崩せなかった観点を一覧にする。

再レビューの場合は、さらに次を含める。

- 前回の指摘一覧と、それぞれへの対応（修正内容 or 却下理由）
- 「修正が本当に問題を解消したか、修正が新たなバグを生んでいないか、却下理由が妥当かを検証し、不当な却下には反論すること」

依頼したら、taskId を伝えてターンを終える。完了通知で再開する。

## 3. 結果を検証して報告する

指摘は自分のコードへの批判なので、判定は**反証責任を自分に置く**:

- 却下するには、指摘の失敗シナリオが起きないことを示す具体的な根拠（該当コード行、実行したテストの結果など）が要る。根拠を示せなければ「採用」か「要確認」にする。
- 失敗シナリオが再現できるものは、実際に再現してから判定する。

全件を次の表で報告する。

| 重大度 | 指摘 | 判定（採用 / 却下 / 要確認） | 根拠・対応案 |

表の下に、Sol が崩せなかった観点の一覧と、レビュー原文へのリンク `[Sol レビュー](t3-thread://v1/<childThreadId>)` を付ける。修正はユーザーの確認を得てから行う。

## 再レビュー

修正後に再レビューを頼まれたら、前回の子スレッドへの `t3_thread_send` ではなく、新しい `delegate_task` で手順 2 からやり直す。
